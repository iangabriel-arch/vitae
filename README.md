# Vitae — Blood Donation Coordination App

A tightly-scoped blood donation coordination platform for Kenya, focused
solely on the donor-request-match loop. See the project plan for full
rationale, scope boundaries, security model, and roadmap.

## Repo structure

```
vitae/
├── backend/
│   ├── app/
│   │   ├── main.py          # FastAPI app + router wiring
│   │   ├── models/          # SQLAlchemy models (users, blood_requests, donor_matches, donations, blood_banks)
│   │   ├── schemas/         # Pydantic request/response models
│   │   ├── routers/         # one file per resource
│   │   ├── core/            # config, security (hashing/JWT), db session, auth dependency
│   │   └── services/        # matching + notification logic (stubs — fill in next)
│   ├── alembic/              # DB migrations
│   ├── requirements.txt
│   ├── docker-compose.yml
│   └── .env.example
├── frontend/                 # React/Next.js app (not yet scaffolded)
├── .gitignore
└── README.md
```

## Getting started (backend)

```bash
cd backend

# 1. Start local Postgres
docker compose up -d

# 2. Create a virtualenv and install deps
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

# 3. Copy env file and adjust if needed
cp .env.example .env

# 4. Run migrations — creates the five schema tables
alembic upgrade head

# 5. Run the API
uvicorn app.main:app --reload
```

Then check `GET http://localhost:8000/health` → `{"status": "ok"}`.
Interactive API docs (auto-generated by FastAPI) are at `/docs`.

## Current state of this skeleton

- **Working**: app boots, `/health` returns 200, DB models + first Alembic
  migration match the schema in the project plan, all routes from the API
  contract exist with the correct method/path/auth shape.
- **Stubbed (returns `501 Not Implemented`)**: the actual business logic for
  every route except `/health` and `GET /users/me`. Each stub has a `TODO`
  comment describing what it needs to do.
- **Not started**: frontend, notification sending (email), rate limiting,
  audit logging, MFA, USSD/SMS fallback (all later-phase per the roadmap).

## Suggested build order

1. Wire up `auth.py` (register/login) — everything else needs a real user.
2. Implement `users.py` (`PATCH /users/me`, `/donors/search`).
3. Implement `requests.py` (`POST /requests` + the matching pipeline in
   `services/matching.py`).
4. Implement `matches.py` (donor accept/decline, mark-donated).
5. Implement `donations.py` (log + eligibility).
6. `blood_banks.py` — simplest resource, good for seeding sample data early.
7. Rate limiting on `/donors/search` and `/requests` before this touches
   real user data (see Security & Compliance section of the project plan).

## Notes

- The first Alembic migration (`0001_initial_schema`) was hand-written to
  match the schema exactly, since it couldn't be generated against a live
  DB in this environment. Once you run it against your local Postgres,
  running `alembic revision --autogenerate -m "check drift"` should
  produce an empty migration — that's your signal the models and DB agree.
- `SECRET_KEY` in `.env.example` is a placeholder. Generate a real one
  before anything beyond local dev, e.g. `python -c "import secrets; print(secrets.token_hex(32))"`.
